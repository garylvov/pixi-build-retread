## DESIGN

A. Per-wheel git provenance (schema bump to 8): add GitWheelSource{url, rev:RESOLVED-SHA, subdirectory:Option, extras:Vec} as Option<GitWheelSource> git_source on LockWheel (serde-default None, skip_serializing_if). Thread through ResolvedWheel.git_source -> EmitWheel.git_source -> LockWheel.git_source. Producer sets it in materialize_and_rewrite git arms (named src/handler/mod.rs:3298-3332, inline 3362-3388). plan() does NOT read git_source (keeps #4 parity).
   Replayer: rewrite Class-1 arm (src/handler/mod.rs:4079-4129) to PREFER lw.git_source -> build synthetic WheelEntry{git:url,rev:SHA,subdirectory,extras} -> materialize_and_rewrite (manifest-independent). Legacy fallback to config.retread_wheels only if git_source absent. This UNIFIES Class-1 (genesis inline + newton named both collapse to inline url+rev synth) AND any future Class-3 with one code path.

   NAMED-vs-INLINE PARITY IS PRE-RESOLVED (no runtime escalation expected). The grizzly proved both arms call the IDENTICAL build_wheel_from_git: named arm at src/handler/mod.rs:3310, inline arm at 3369, both with the same six-arg signature (url, rev, subdir, cache_dir, out_dir, python_version), and both delegate checkout-root computation to the single checkout_root_for_entry (src/handler/mod.rs:3221-3240) -> single git_checkout_root. Extras do NOT reach the wheel build (they are folded into courier_input_specs and drive BFS closure expansion only; they are NOT passed to build_wheel_from_git). Therefore collapsing a named-git entry to an inline synth {git:url, rev:SHA} at replay produces a BYTE-IDENTICAL wheel to the named-git arm. Commit 5's parity test CONFIRMS this; no runtime escalation path is added.

   SINGLE-ENTRY GUARD (known limitation): named-vs-inline byte-identity AND the skip_subdirs=[] replay safety rely on each git bundle being SINGLE-ENTRY (exactly one git checkout root). genesis (1 git entry) and newton (1 git entry) are safe. A future MULTI-entry shared-checkout git bundle (>1 [retread-wheels] entry resolving to the same checkout, or distinct subdirs of one clone) would build a NON-TRIVIAL skip_subdirs at produce time; the replay synth uses skip_subdirs=[], which would NOT reproduce that build -> would break byte-identity. AMEND: add an explicit assertion/guard in the replayer (assert single git checkout root per bundle, hard-error with a directing message otherwise) + a doc comment marking this as a known Phase-2 limitation deferred to Phase 3.

B. A-0 latent parse bug (auto_bundle.rs extra_dep_source_from_url, src/handler/auto_bundle.rs:693-715): the fn does NOT strip a `#subdirectory=` fragment -> for a `git+https://host/repo@rev#subdirectory=pkg` URL, `rfind('@')` leaves `#subdirectory=pkg` appended to the rev string (rev corrupted to "rev#subdirectory=..."). Fix: split rev on '#', parse the subdirectory= fragment; add a subdirectory field to ExtraDepSource::Git (src/handler/auto_bundle.rs:784) + PendingSource::Git (src/handler/auto_bundle.rs:592) + the synthetic WheelEntry construction in the BFS path (src/handler/mod.rs:2947-2951).

   SEQUENCING — SPLIT FROM THE EPOCH BUMP. This parse fix is a NO-OP for both real packs: genesis and newton have ZERO @git+ transitives, so extra_dep_source_from_url is never reached for either, and the fix CANNOT change a single emitted byte for any pack lacking git transitives. Bumping EMIT_EPOCH alongside it would gratuitously invalidate EVERY committed lock (isaac6 + genesis + newton) for zero current benefit. AMEND: land the parse fix DEFENDED BY A UNIT TEST and DO NOT bump EMIT_EPOCH in that commit. The epoch bump is deferred: either (a) bump when a real Class-3 pack (git transitive) first exists, OR (b) fold the bump into the schema-driven lock regen (commit 6) with an inline comment proving why — but since no current pack emits different bytes from this fix, option (a) is preferred and (b) is documented as the fallback. The committed plan does NOT bump EMIT_EPOCH for the A-0 fix.

C. HEAD->SHA: BFS defaults rev="HEAD" (src/handler/mod.rs:2949) non-reproducible; git cache key (git_checkout_root, src/source_build.rs:230-243) keys sha256(url + "\0" + rev) — keying a literal "HEAD" is a stale-checkout hazard. build_wheel_from_git (src/source_build.rs:252-323) must return (PathBuf, resolved-SHA) via `git rev-parse HEAD` post-checkout; store SHA in git_source; replay clones key on the resolved SHA (stable). Real packs already pin SHAs at config level; this generalizes + makes the lock manifest-independent.

D. Poisoning: config-entry git revs ARE in inputs_hash (courier_input_specs — inline rev folded src/courier.rs:71, named-source rev folded src/courier.rs:77). genesis(inline)+newton(named) both hashed -> moved config rev invalidates -> cascade. BFS-transitive git revs NOT hashed (none in real packs). RECOMMENDATION: replay pins the RECORDED SHA; only a cascade re-resolves a moving branch (branch-rev semantics: a branch/HEAD rev resolves to a SHA at produce time and is pinned in the lock; the lock then replays that SHA byte-stably; a new branch tip is only picked up by a fresh cold solve, which is correct — the lock is the contract). Document (do NOT fold output SHAs into the input hash = circular). Add // POISONING comments.

E. DETERMINISM / lock parity (LOAD-BEARING — DOWNGRADED from CONFIRMED). The lock stores NO wheel sha256; git_source stores url+SHA+subdir+extras (inputs, not byte-derived). Two builds of the same commit yield the same git_source. BUT the wheel FILENAME and VERSION are emitted by the UPSTREAM build backend, not by retread, so byte-identity of the lock is conditional:
   - Reproducible IFF the upstream emits a STATIC version at the pinned SHA. True for genesis-world (1.1.1) and newton (1.3.0) ONLY because their upstream build configs bake static versions at the pinned SHA.
   - A setuptools_scm project WITHOUT a reachable tag in the clone emits `X.Y.dev<count>+g<sha>.d<YYYYMMDD>`. The `.d<YYYYMMDD>` suffix DRIFTS version -> filename -> lw.version / lw.filename -> LOCK DRIFT across calendar days with NO inputs_hash change. SOURCE_DATE_EPOCH does NOT help here (setuptools_scm's local date segment is wall-clock, and the version is not byte-derived from anything retread hashes).
   - WORDING: "Reproducible IFF upstream emits a static version at the pinned SHA; setuptools_scm-without-reachable-tag yields a date suffix -> drift." NOT "CONFIRMED / SOURCE_DATE_EPOCH NOT needed."
   - GUARD (commit 1): after build_wheel_from_git, detect a non-reproducible version. Regex the emitted wheel version/filename for `\.dev\d+`, `\.d\d{8}`, and a local `+g<sha>` segment. At MINIMUM emit a loud `tracing::warn!` (better: hard-error directing the user to pin a tag/version, or set `SETUPTOOLS_SCM_PRETEND_VERSION`). The plan ships at least the warn!; the hard-error/pretend-version path is documented as the stronger option.
   - CHEAP INSURANCE (commit 1): add `git fetch --tags` (or fetch the tag alongside the rev) in the build_wheel_from_git fallback branch (src/source_build.rs:295-310 — note: TODAY this branch does only `git fetch origin <rev>` then `git checkout FETCH_HEAD`, with NO `--tags`). Fetching tags lets setuptools_scm find a reachable tag and emit a static version instead of a dev/date suffix.

F. sdist + BFS direct-URL: neither real pack hits them. DOCUMENT residual fall-through (Ok(None) -> full resolve), do NOT add speculative WheelSource variants.

G. SCHEMA baseline reconciliation. The COMMITTED genesis + newton locks are schema 4 (NOT 7). The live SCHEMA constant has since moved to 7 (src/lock.rs:135). So this migration is effectively schema-OLD -> 8. The `!= SCHEMA` gate today rejects any non-current schema and falls through to full resolve, so ALL old-schema locks (schema 4 included) fall through CLEANLY — no migration code needed, no panic. Migration target: bump SCHEMA 7 -> 8 to carry GitWheelSource. serde-default None on git_source means schema-8 locks lacking it (and any older lock that slips through) deserialize safely; but the != gate means pre-8 committed locks are re-derived on first build, which commit 6 regenerates. SCHEMA bump is NOT an EMIT_EPOCH bump (lock FORMAT changed, not emitted-output SEMANTICS for identical inputs).
